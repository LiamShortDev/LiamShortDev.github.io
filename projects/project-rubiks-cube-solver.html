Rubik's Cube Solver & Trainer

Introduction

A desktop application developed as an A-Level Computer Science project to help users learn and practise Rubik's Cube solving algorithms. Rather than simply finding a short solution, the application teaches the cube using the human CFOP method and provides tools for learning, practising and applying algorithms.

The project combines a custom Rubik's Cube state model, 2D geometric rendering, heuristic search, algorithm recognition, a local database and an interactive Windows interface.

Tech Stack

  • C#
  • Windows Forms (WinForms)
  • Object-Oriented Programming
  • Custom 2D / Isometric Cube Rendering
  • Microsoft Access / OleDb Database
  • SHA-256 Password Hashing
  • IDA* Heuristic Search

The Application

The application provides a digital cube that can be manipulated using standard face-move controls. Users can generate a 20-move scramble, create a new cube, recolour tiles, save and load cube states, and access the trainer or CFOP solver.

Cube validation prevents invalid states from being passed into the solver, while user-specific data can be saved locally for later use.

Solving with CFOP

The solver is designed around the human CFOP method rather than a generic shortest-path solution. Each stage is completed before the next becomes available, allowing the generated solution to be followed and understood.

  • White Cross: heuristic IDA* search is used to find a move sequence for the cross.
  • F2L: edge and corner pairs are identified and matched against stored algorithms.
  • OLL: cases are detected and solved using first- and second-look algorithms.
  • PLL: permutation cases are detected and solved using first- and second-look algorithms.
The important design decision was to optimise for a solution that is understandable to a human CFOP learner, rather than simply minimising the total number of moves.

Cube State & Move System

The cube is represented internally using arrays of coloured tiles. Face rotations and layer movements modify this state, allowing the same representation to drive both the solver and the visual display.

Standard Rubik's Cube notation is used throughout the application, keeping the generated solutions compatible with conventional CFOP learning.

2D Cube Rendering

Instead of using a dedicated 3D graphics engine, the cube was rendered as a 2D isometric projection. Polygon geometry was calculated using trigonometry to position the visible stickers and construct the cube faces.

This approach kept the project within scope while giving complete control over how cube rotations and sticker colours were displayed.

Heuristic Search

The White Cross solver uses Iterative Deepening A* (IDA*). The algorithm combines iterative depth limits with a heuristic estimate of the remaining moves, reducing memory usage compared with a conventional A* search.

The heuristic does not guarantee a globally optimal solution, but provides a practical balance between search efficiency and move count for the intended CFOP workflow.

Algorithm Trainer

The trainer allows users to browse and practise stored CFOP algorithms. Standard algorithms and user-defined algorithms can be stored and selected, with the cube state and notation used to demonstrate when an algorithm should be applied.

This makes the trainer more than a static algorithm list: the user can connect a recognised cube case with the notation and the resulting sequence of moves.

Data & Security

A local Microsoft Access database stores user and algorithm data, allowing the application to operate offline. Usernames are used to associate saved data with individual accounts, while passwords are stored as salted SHA-256 hashes rather than plain text.

The database also provides a flexible way to store the CFOP algorithms, allowing the trainer to be extended without changing the core application logic.

Testing & Validation

The application was tested across its main functional areas, including login, navigation, cube manipulation, scrambling, saving and loading, cube validation, algorithm training and solver behaviour.

Testing was also used to identify and correct implementation issues. For example, a scramble test identified that the program could generate 21 moves instead of the required 20, which was corrected by fixing the loop count. A trainer playback issue caused by the timer implementation was also identified and corrected.

What I Learned

This project developed my understanding of algorithm design, state representation and object-oriented programming. Building the solver also required thinking carefully about how a heuristic can make a search problem practical rather than relying on brute-force exploration.

The rendering system gave me experience translating a mathematical model into a visual interface, while the database and testing work reinforced the importance of separating application functionality from persistent data and validating individual features systematically.

If I Did It Again...

The next major improvement would be a fully interactive 3D cube using a graphics library, allowing users to manipulate the cube naturally with mouse controls and animated rotations.

I would also explore connecting the software to a physical cube using sensors, allowing real cube states to be detected automatically and fed directly into the solver and trainer.
